# LLM Wiki

一种用 LLM 构建个人知识库的模式。

本文档是一份「思路文件」，设计意图是可以被复制粘贴到你自己用的 LLM Agent（例如 OpenAI Codex、Claude Code、OpenCode / Pi 等）。目标是传达高层思路，具体细节由你的 agent 与你协作完成。

## 核心理念

大多数人使用 LLM 处理文档的经验都像 RAG：上传一堆文件，LLM 在提问时检索相关片段，然后生成答案。这能跑，但 LLM 每次提问都从零重新发现知识。没有累积。问一个需要综合五份文档才能回答的微妙问题时，LLM 每次都要重新寻找并拼接相关片段。没有沉淀。NotebookLM、ChatGPT 文件上传、大多数 RAG 系统都是这个模式。

这里的思路不同。LLM 不是只在提问时从原始文档里检索，而是**增量地构建并维护一个持久化的 wiki**——一个位于你和原始素材之间的、结构化且相互链接的 markdown 文件集合。当你加入一份新素材时，LLM 不会只是为后续检索建索引。它会阅读它、抽取关键信息，并整合进已有 wiki——更新实体页、修订主题摘要、标注新数据与旧论断冲突之处、强化或挑战不断演进的综合判断。知识被一次性编译，然后**保持最新**，而不是每次查询都重新推导。

这是关键区别：**wiki 是一个持久的、可累积的产物。** 交叉引用已经在那儿了。矛盾已经被标记了。综合判断已经反映了你读过的所有内容。每加入一份素材、每问一个问题，wiki 都变得更丰富。

你（几乎）从不亲自写 wiki——LLM 写并维护所有内容。你负责素材筛选、探索方向、提出正确的问题。LLM 做所有苦活——摘要、交叉引用、归档、簿记——这些让知识库能随时间真正有用的工作。实践中，我会让 LLM agent 开在一边，Obsidian 开在另一边。LLM 根据我们的对话做修改，我在 Obsidian 里实时浏览结果——跟随链接、看图谱视图、读更新过的页。Obsidian 是 IDE，LLM 是程序员，wiki 是代码库。

这个模式能套到很多场景。例如：

- **个人**：追踪自己的目标、健康、心理、自提升——归档日记、文章、播客笔记，随着时间构建你自己的结构化画像
- **研究**：数周或数月地深入一个主题——读论文、文章、报告，增量构建一份带不断演进论点的综合 wiki
- **读一本书**：边读边归档每章，建立人物、主题、情节线的页面，并把它们互相连接起来。读完后你就有一份丰富的伴读 wiki。可以想象粉丝 wiki 像 [Tolkien Gateway](https://tolkiengateway.net/wiki/Main_Page)——数千个互相链接的页面覆盖人物、地点、事件、语言，由志愿者社区花数年共建。你可以在阅读过程中亲自建出这种东西，让 LLM 做所有交叉引用与维护工作
- **业务 / 团队**：由 LLM 维护的内部 wiki，由 Slack 线程、会议记录、项目文档、客户通话喂入。可以有人参与审核更新。wiki 保持新鲜，因为 LLM 做了团队里没人想做的维护工作
- **竞品分析、尽调、旅行规划、课程笔记、爱好深挖**——任何你在一段时间里累积知识、想要它被组织而非散落的场景

## 架构

三层结构：

**Raw sources（原始素材）**——你策展的素材文档集合。文章、论文、图片、数据文件。这些是不可变的——LLM 只读取、绝不修改它们。这是你的事实来源。

**The wiki**——LLM 生成的 markdown 文件目录。摘要、实体页、概念页、对比、概览、综合判断。LLM 完全拥有这一层。它创建页面、在新素材到来时更新它们、维护交叉引用、并保持一致性。你读它，LLM 写它。

**The schema（模式文档）**——一份文档（例如 Claude Code 的 `CLAUDE.md` 或 Codex 的 `AGENTS.md`），告诉 LLM wiki 是怎么组织的、约定是什么、在摄取素材、回答问题、维护 wiki 时遵循什么工作流。这是关键的配置文件——它让 LLM 成为纪律化的 wiki 维护者，而不是通用 chatbot。你和 LLM 一起随时间演进它，因为你们会逐渐弄清对你的领域什么最有效。

## 操作

**Ingest（摄取）**。你把新素材丢进原始集合，让 LLM 处理它。一个示例流程：LLM 读素材、和你讨论关键要点、在 wiki 里写一份摘要页、更新索引、更新 wiki 里相关的实体和概念页、向 log 追加一条记录。单个素材可能触及 10-15 个 wiki 页。我个人倾向于一份一份地摄取并保持参与——我读摘要、看更新、指导 LLM 该强调什么。但你也可以少监督地批量摄取多份素材。开发适合你风格的工作流并把它文档化到 schema 里给将来 session 用，取决于你。

**Query（查询）**。你向 wiki 提问。LLM 搜索相关页面、阅读它们、用引用合成答案。答案可以随问题形式变化——一份 markdown 页、一个对比表、一份幻灯片（Marp）、一张图表（matplotlib）、一张 canvas。重要洞见：**好答案可以归档回 wiki 成为新页面。** 你问出来的对比、分析、你发现的连接——这些有价值，不该消失在聊天记录里。这样你的探索像被摄取的素材一样在知识库里累积。

**Lint（体检）**。周期性让 LLM 健康检查 wiki。检查：页之间的矛盾、被新素材取代的过时论断、没有任何入向链接的孤儿页、被提及但没有独立页的重要概念、缺失的交叉引用、可以用网络搜索填补的数据空白。LLM 擅长建议新问题去调查、新素材去搜。这让 wiki 长大时保持健康。

## 索引与日志

两个特殊文件帮助 LLM（也帮助你）在 wiki 长大时导航它。它们有不同的用途：

**index.md** 是内容导向的。它是 wiki 里所有内容的目录——每个页面带链接、一句话摘要、可选的元数据如日期或素材数。按类别组织（实体、概念、素材等）。LLM 每次摄取时更新它。回答查询时，LLM 先读 index 找相关页，再钻进去细读。这在中等规模（~100 份素材、~几百页）下出奇地好用，并且省去了基于 embedding 的 RAG 基础设施。

**log.md** 是时序的。它是一个只追加的记录，记录发生了什么、什么时候——摄取、查询、lint 通过。一个有用的提示：如果每条记录以一致前缀开头（例如 `## [2026-04-02] ingest | Article Title`），log 就能用简单的 unix 工具解析——`grep "^## \[" log.md | tail -5` 给你最近 5 条。log 给你 wiki 演进的时间线，并帮助 LLM 理解最近做过什么。

## 可选：CLI 工具

某一天你可能想建一些小型工具帮 LLM 更高效地操作 wiki。最直观的是一个 wiki 页面的搜索引擎——小规模下 index 文件够了，但 wiki 长大你想要正经搜索。[qmd](https://github.com/tobi/qmd) 是个不错的选择：它是 markdown 文件的本地搜索引擎，带混合 BM25 / 向量搜索和 LLM 重排，全部在设备上跑。它既有 CLI（所以 LLM 可以 shell 出调它）也有 MCP server（所以 LLM 能把它当原生工具用）。你也可以自己建更简单的——LLM 可以帮你 vibe-code 一个朴素的搜索脚本，按需迭代。

## 技巧与诀窍

- **Obsidian Web Clipper** 是一个浏览器扩展，把网页文章转成 markdown。非常有用，能快速把素材送进你的原始集合
- **把图片下载到本地**。在 Obsidian 设置 → 文件与链接里，把「附件文件夹路径」设到固定目录（例如 `raw/assets/`）。然后在设置 → 快捷键里搜「Download」找到「Download attachments for current file」并绑到快捷键（例如 Ctrl+Shift+D）。剪藏完一篇文章后，按下快捷键，所有图片都下到本地磁盘。这可选但有用——它让 LLM 能直接查看并引用图片，而不是依赖可能失效的 URL。注意 LLM 不能一次性原生读取带内联图片的 markdown——变通方法是让 LLM 先读文本，然后单独查看部分或全部被引用的图片以获得额外上下文。有点笨拙但够用
- **Obsidian 的图谱视图** 是看你的 wiki 长什么样的最佳方式——什么连接着什么、哪些页是枢纽、哪些是孤儿
- **Marp** 是一种基于 markdown 的幻灯片格式。Obsidian 有插件支持它。直接从 wiki 内容生成演示文稿很有用
- **Dataview** 是一个 Obsidian 插件，能跑页面 frontmatter 上的查询。如果你的 LLM 给 wiki 页加了 YAML frontmatter（标签、日期、素材数），Dataview 能生成动态的表格和列表
- wiki 就是一个 markdown 文件的 git 仓。版本历史、分支、协作免费拿到

## 为什么这能 work

维护知识库的繁琐部分不是阅读或思考——是簿记。更新交叉引用、保持摘要最新、标注新数据何时与旧论断冲突、在几十个页之间维持一致性。人类放弃 wiki 是因为维护负担增长比价值快。LLM 不会觉得无聊、不会忘记更新一条交叉引用、能在一轮里改 15 个文件。wiki 能保持维护，因为维护成本接近零。

人的工作是策展素材、指导分析、问好问题、思考这一切意味着什么。LLM 的工作是其他所有事情。

这个思路在精神上与 Vannevar Bush 的 Memex（1945）相关——一个个人的、策展的知识存储，文档之间带联想链。Bush 的愿景比最终出现的 web 更接近这个：私有的、主动策展的、文档之间的连接与文档本身一样有价值。他没能解决的部分是谁来做维护。LLM 解决了。

## 说明

本文档刻意保持抽象。它描述的是思路，不是具体实现。具体的目录结构、schema 约定、页面格式、工具——所有这些都取决于你的领域、你的偏好、你的 LLM 选择。上面提到的所有东西都是可选的、模块化的——有用的就用，没用的就忽略。例如：你的素材可能只有文本，所以你完全不需要图片处理。你的 wiki 可能小到 index 文件就够了，不需要搜索引擎。你可能不关心幻灯片，只要 markdown 页。你可能想要完全不同的输出格式。正确的用法是把这份文档分享给你的 LLM agent，协作实例化一个适合你需要的版本。本文档唯一的工作是传达这个模式。你的 LLM 能搞定剩下的。
